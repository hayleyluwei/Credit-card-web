# 攻略文章上稿流程

最後更新：2026-08-18（Asia/Taipei）
用途：把寫好的攻略文章正確送進資料庫並上線的固定流程。
分工：**內容怎麼寫**看 `GUIDE_ARTICLE_WRITING_攻略文章撰寫準則.md`；**寫好之後怎麼上**看本文件。

---

## 0. 三個必須先知道的前提

### (1) 唯一入口是後台，沒有匯入腳本

優惠資料有 `npm run data:import` 可以從試算表批次匯入，**攻略文章沒有**。
唯一途徑是登入後台 `/admin/articles` 手動建立。

### (2) 後台直接連正式站資料庫

本專案沒有獨立的開發資料庫，`.env` 的 `DATABASE_URL` 直接指向正式站 Neon。
**在後台按下「建立」的那一刻，資料就進了正式站。** 沒有測試環境可以先試。

好消息是這一步仍然安全：新建文章的 `isPublished` 預設為 `false`，草稿**不會**出現在前台。

### (3) ⚠️ 草稿無法預覽

`/guides/[slug]` 對未發布的文章直接回 404，`/guides` 列表也只列已發布的。
**這代表你沒有辦法在發布前看到文章實際長什麼樣子。**

所以本流程把檢查全部放在「上稿前」與「發布後立刻」兩端：
上稿前用 Markdown 檢查內容，發布後第一時間看前台，有問題就馬上改或退回草稿。

---

## 1. 上稿前檢視清單

> 這一節就是「文章要依照上稿流程檢視」的實際內容。逐項確認後再進後台。

### A. 內容

依 `GUIDE_ARTICLE_WRITING_攻略文章撰寫準則.md` 自我檢查，重點：結論先行、每個數字有官方來源與查證日期、
術語白話、比較表欄位齊全、不抄襲官網文案。此處不重複。

### B. 標題與 SEO 欄位

| 欄位 | 用途 | 留空的話 | 檢查重點 |
|---|---|---|---|
| `title` | 前台 H1、`/guides` 列表標題 | **必填** | 一眼看得出在講哪個情境；避免「2026 最新懶人包」這種無資訊量的字 |
| `summary` | 列表摘要、SEO description 的第一備援 | 可空 | 一到兩句講完結論。留空會讓 SEO 描述退到預設字串，很不利 |
| `seoTitle` | 瀏覽器分頁與搜尋結果標題 | 自動用 `{title}｜信用卡優惠查詢網站` | 只有在 `title` 太長或想加關鍵字時才另外填 |
| `seoDescription` | 搜尋結果摘要 | 依序退到 `summary` → 預設字串 | 建議 60–120 字，含情境關鍵字 |

### C. slug（**最重要，發布後幾乎不能改**）

slug 就是網址：`/guides/{slug}`。目前**沒有任何轉址機制**（T25 尚未核准），
一旦發布後又改 slug，舊網址就直接死掉——外部連結、搜尋引擎索引、已分享的連結全部斷掉。

檢查：

1. **留空會由標題自動產生。中文標題產生出來的 slug 通常不理想，請一律手動填。**
2. 用小寫英文與連字號，例如 `tax-payment`、`tuition-2026`。
3. **如果這篇要出現在對應的情境頁，slug 必須與情境 slug 完全相同。**
   情境頁的關聯方式是「slug 相同即視為對應攻略文」，差一個字就不會連上。

   目前 14 個情境 slug（固定清單，不可自創）：

   ```
   tax-payment   tuition       utilities     insurance-premium
   gas           food-delivery supermarket   travel-booking
   subscription  movies        hsr-tra       etag
   parking       roadside-assistance
   ```

   例：寫「繳稅」攻略且希望它出現在 `/scenarios/tax-payment` 的「延伸閱讀」，
   slug 就必須是 `tax-payment`。

4. 不打算對應情境頁的文章，slug 自由命名，但仍要**確認前台沒有同名文章**（slug 唯一，重複會擋下來）。

### D. 連結檢查

> 死連結是風格契約與 T29 都明令禁止的事項，這一項不能跳過。

| 檢查 | 做法 |
|---|---|
| 站內連結格式 | 用相對路徑 `/offers/xxx`、`/scenarios/xxx`、`/categories/xxx`、`/cards/xxx`，不要寫完整網域 |
| **站內連結目標真的存在** | 逐一在正式站開一次。優惠 slug 要與資料庫一致，憑印象打的 slug 幾乎一定錯 |
| 官方來源連結 | 逐一點開，確認沒有失效、沒有導到首頁、確實是文中引用的那一頁 |
| 連結文字 | 不要用「點這裡」；用能看出目的地的文字 |

**目前的限制**：文章導回優惠只能靠你在 Markdown 裡自己寫連結。
制度化的「導回優惠」出口是 T29 的 Scope B，**尚未核准實作**。

### E. FAQ JSON（有填才需要檢查）

格式是物件陣列，欄位名稱固定為 `question` 與 `answer`：

```json
[
  { "question": "繳稅刷卡有手續費嗎？", "answer": "多數銀行的分期方案免手續費，但一次付清通常要收。" },
  { "question": "回饋上限怎麼算？", "answer": "以活動期間內累積計算，各卡規則不同。" }
]
```

系統存檔時會驗證格式，錯了會擋下來並顯示訊息。常見錯誤：中文引號、最後一項多一個逗號、欄位名稱打錯。

### F. 查證日期 `lastVerifiedAt`

填**你實際核對官方頁面的那一天**，不是寫稿日、也不是上稿日。這個日期會顯示在前台，是文章可信度的依據。

---

## 2. 上稿步驟

1. 登入後台 → 攻略文章管理 → 新增。
2. 依上一節的清單填入所有欄位。**特別確認 slug**。
3. 儲存。此時文章是**草稿**，前台看不到。
4. 回列表確認該篇存在、slug 正確。
5. **slug 若填錯，現在就是最後的修改時機**——發布之後再改就會斷鏈。

---

## 3. 發布

在列表按「切換發布」。系統會：

- 設 `isPublished = true`
- **第一次發布時**才寫入 `publishedAt`（之後取消再重新發布不會覆蓋，發布時間維持第一次那一天）
- 重新驗證 `/guides`、`/guides/{slug}`、`/sitemap.xml`

---

## 4. 發布後立刻驗證

> 因為沒有預覽，這一步等於是「校稿」。發現問題就馬上退回草稿再修。

| # | 檢查 | 預期 |
|---|---|---|
| 1 | 開 `/guides` | 新文章出現在列表，標題、摘要、查證日期正確 |
| 2 | 開 `/guides/{slug}` | 頁面正常開啟，H1、摘要、內文排版正確 |
| 3 | Markdown 呈現 | 表格有框線、清單有項目符號、標題層級正確，沒有跑出生的 `#` 或 `|` |
| 4 | 逐一點內文所有連結 | 全部能開，沒有 404 |
| 5 | FAQ 區塊 | 有填的話正常顯示 |
| 6 | 查證日期 | 顯示的日期與你填的一致（T30 修正後應為台北日期） |
| 7 | 手機檢視 | 表格可橫向捲動、不破版 |

### ⚠️ 第 8 項要特別注意：情境頁的「延伸閱讀」不會自動出現

`/scenarios/[slug]` 是 **build 時靜態產生**的頁面，而文章的發布動作
**沒有**重新驗證這個路徑。

**所以：發布文章後，對應情境頁的「延伸閱讀」區塊要等下一次重新部署才會出現。**

處理方式：發布後如果需要情境頁立刻連上，要另外觸發一次部署（**需先取得使用者授權 push／部署**，
見 2026-08-09 的 Git 授權規則）。若不急，就等下一次正常部署一起生效。

| 頁面 | 發布後是否立刻反映 |
|---|---|
| `/guides`、`/guides/{slug}`、`/sitemap.xml` | 是（發布動作有重新驗證） |
| **`/scenarios/{slug}` 的延伸閱讀** | **否，需重新部署** |

---

## 5. 目前的已知限制（都不是 bug，是還沒做的功能）

| 限制 | 對應任務 | 影響 |
|---|---|---|
| 沒有草稿預覽 | 無 | 只能發布後校稿 |
| 沒有 slug 轉址 | T25（草案） | slug 發布後不可改 |
| 文章導回優惠沒有制度化出口 | T29 Scope B（草案） | 只能手寫 Markdown 連結 |
| 情境頁需重新部署才連上文章 | 無 | 見上一節 |
| 沒有匯入腳本 | 無 | 只能後台逐篇建立 |

---

## 6. 給 AI 的界線

- 本流程**不授權** AI 代為建立、修改或發布文章。寫入資料庫屬第三層操作，每次都要使用者個別確認。
- AI 可以做的：依本清單審稿、檢查 slug 與情境對應、驗證連結是否存在、檢查 FAQ JSON 格式、
  發布後以唯讀方式核對前台呈現。
- AI 不得代填 `lastVerifiedAt`——那是「人實際查證過」的宣告。
