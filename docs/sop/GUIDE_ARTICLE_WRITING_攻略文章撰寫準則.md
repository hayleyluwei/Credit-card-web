# 攻略文章撰寫準則

最後更新：2026-07-30（Asia/Taipei）
用途：撰寫 `/guides/[slug]` 攻略文章時的固定準則，對應任務卡 `docs/implementation/tasks/T20-GUIDE_ARTICLES_攻略文章功能.md`（v3）。

## 1. 結論先行

文章開頭（摘要或第一段）先給結論，不要把判斷留到文末。讀者與 AI 摘要工具都優先讀前段內容。

例：「2026 年繳稅，A 銀行 B 卡回饋最高、C 銀行 D 卡免手續費上限最高，以下逐一比較。」而不是先鋪陳背景故事。

## 2. 每個數字附官方來源與查證日期

文中提到的回饋率、上限、門檻、活動期間等數字，必須能對應到官方來源網址與查證日期。不確定或無法查證的數字不要寫進文章，或明確標註「請以官網最新公告為準」。

## 3. 術語白話

避免只寫銀行內部術語（例如「大戶」「指定任務」）而不解釋。第一次出現時用白話說明門檻或條件，仿照 `docs/data-collection/DATA_COLLECTION_SPEC...` 的「術語白話原則」。

## 4. 比較表格式

跨卡片比較用 Markdown 表格（`remark-gfm` 支援），欄位建議：卡片名稱、回饋率／內容、回饋上限、活動期間、適用條件。表格內容需與資料庫或官網一致，不得憑印象填寫。

## 5. FAQ 寫法

- 每篇文章的 `faqJson` 建議 3-6 題，聚焦讀者實際會問的問題（例如「這個優惠所有信用卡都適用嗎」「回饋是自動累積還是要登錄」）。
- 格式：`[{"question":"問題","answer":"答案"}]`，純 JSON 陣列，不要多餘的逗號或註解。
- 答案簡短直接，避免重複文章內文全文。

## 6. 內文格式限制

- 內文為 Markdown（`contentMd`），**不接受 raw HTML**：前台 `react-markdown` 預設不會執行內文中出現的 `<script>` 等標籤，會直接以純文字顯示，這是防 XSS 的安全機制，撰寫時不要嘗試插入 HTML 排版。
- 支援標準 Markdown 語法（標題、清單、粗體、連結、表格）。

## 7. 更新與查證日期

- `lastVerifiedAt` 記錄最後一次核對官方來源的日期，內容有變動（例如優惠更新、數字變動）時務必更新此欄位。
- 前台會顯示「最後更新」（`updatedAt`，系統自動）與「最後查證」（`lastVerifiedAt`，人工填寫）兩個日期，兩者意義不同：前者是任何欄位異動都會更新，後者專指人工核對官方來源的時間點。

## 8. 與情境頁（`/scenarios/[slug]`）的分工

- 情境頁是「優惠速覽清單」：自動列出符合某個情境標籤的已發布優惠，不含判斷與比較。
- 攻略文章是「深度整理」：結論、比較表、FAQ，是情境頁做不到的內容。
- 若某情境已有攻略文章（文章 slug 與情境 slug 相同時系統會自動顯示交叉連結），撰寫文章時可以聚焦在情境頁沒有的判斷與比較，不需要重複列出情境頁已有的優惠清單。

## 9. 著作權原則

- 只參考同業或 KOL 文章的資訊架構與選題方向，不得抄錄原文字句。
- 所有數字與條件一律回官方來源查證後改寫，不採用未經查證的二手數字。
