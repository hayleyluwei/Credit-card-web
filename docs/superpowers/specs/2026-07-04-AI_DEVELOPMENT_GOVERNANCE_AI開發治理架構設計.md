# AI 開發治理架構設計

日期：2026-07-04  
專案：信用卡優惠查詢網站  
版本：v2（治理自我檢視修訂版）  
狀態：原始設計已由使用者批准；v2 等待使用者複核後再建立治理文件

## 修訂摘要

v2 補入下列治理細節：

- 平台安全規則與專案規則的優先順序。
- Scope 核准前可更新治理草稿與事實狀態的例外。
- 自動驗證的安全分級及資料保護。
- 任務狀態與部署狀態分離。
- 後續任務索引、任務卡位置與核准證據。
- Git、機密資料、工作區路徑及多 AI 併行保護。
- 治理文件版本策略、人工驗收適用條件與狀態更新順序。
- 以核准白名單取代 AI 對「無副作用測試」的自行判定。
- 以 worktree lock 事前防止多 AI 同時寫入。
- 明確定義 Windows dev server 與 build 前置檢查。
- 將已核准任務卡的明確授權置於 `AI_WORKFLOW` 預設規則之前。

## 1. 設計目的

本設計將信用卡網站後續開發改為一套所有 AI 共用的分層治理流程。核心目標不是讓 AI 無限制自動執行，而是預先定義任務邊界、操作權限、驗收方式與交接規則，減少低價值詢問、上下文重讀、重工與決策疲勞。

本架構涵蓋產品討論、Discovery、工程實作、驗證、人工驗收、任務收尾與新對話交接。Codex、ChatGPT、Claude 或其他可讀取專案文件的 AI，均以同一套文件為準，不各自維護不同版本。

## 2. 設計原則

1. 所有 AI 共用一套唯一規則來源。
2. `AGENTS.md` 只作為核心規則與文件入口，不承載所有細節。
3. 新想法先進行 Discovery；Scope 尚未核准前，不修改系統。
4. Scope 核准後，AI 可在核准範圍內連續修改一般程式碼、文件與測試，完成驗證後一次回報，不逐步詢問。
5. 高風險操作無論是否位於原任務內，都必須停下並取得使用者確認。
6. 目前狀態、任務歷史、完成摘要及 Roadmap 各自有唯一責任，避免同一資訊在多處重複維護。
7. 既有規格書、schema、驗收與任務流程繼續作為專門領域的正式依據；新架構只負責導流，不複製其內容。
8. 所有新治理文件使用繁體中文標題與中文說明；除 `AGENTS.md` 外，英文檔名後以底線接中文用途名稱。
9. 平台、系統、工具與沙箱安全規則永遠優先；專案文件只定義在平台允許範圍內的協作方式。
10. 同一個 Git worktree 同一時間只允許一個 AI 持有寫入鎖並執行寫入型任務；其他 AI 可做唯讀分析，或改用獨立 worktree。
11. 治理文件本身也是受保護的正式規則，除事實狀態與任務紀錄外，不得未經確認修改核心治理規則。

## 3. 文件架構

### 3.1 `AGENTS.md`

用途：所有能讀取專案的 AI 進入專案時的標準入口。

只保留：

- 專案身分與適用範圍。
- 規則優先順序。
- 新對話啟動時的必讀文件。
- 三層操作權限摘要。
- Scope 核准前與核准後的行動邊界。
- 產品規格、schema、驗收及實作任務的專門流程入口。
- 繁體中文、驗證與安全底線。

不再完整重複任務生命週期、驗收表、MVP 詳細邊界及各種修改步驟。這些內容改由下列專門文件承擔。

`AGENTS.md` 是工具慣用的標準檔名，因此不改名；文件內使用中文標題與中文解釋。

### 3.2 `CURRENT_STATE_目前專案狀態.md`

用途：回答「專案現在從哪裡繼續」。

內容包含：

- 最後更新日期、時間與時區，固定使用 `Asia/Taipei`。
- 專案正式路徑及 `git rev-parse --show-toplevel` 的實際結果。
- 目前階段。
- Git branch、HEAD commit 與工作區狀態。
- 目前任務、Scope 版本、核准證據與任務生命週期狀態。
- 最近完成但尚未人工驗收或尚未收尾的項目。
- 本機、Preview 與 Production 的獨立部署狀態；未知時明確標示未知，不自行推定。
- 阻塞事項、待使用者決策事項與下一個建議動作。
- 當前任務文件及最近相關 Summary 的連結。

此文件不保存完整歷史，不複製 T01–T14 的所有完成內容。歷史仍由任務索引與 summaries 保存。

此文件是接續工作的入口，不是 Git 與部署平台的替代品。每個新 session 必須用實際 Git 狀態交叉檢查；若內容已過期，先更新可驗證的事實並回報，不沿用錯誤狀態。

### 3.3 `AI_WORKFLOW_AI協作流程.md`

用途：定義所有 AI 共用的工作方式。

主要內容：

- 問題分類：Bug、UX、功能、產品、架構、Roadmap、交接、驗收、部署或內容工作。
- 任務流程：Discovery → 產品判斷 → 任務卡 → Scope 核准 → 實作 → 自動驗證 → 人工驗收 → 收尾。
- 三層操作權限。
- Scope 核准後的連續實作授權。
- 高風險邊界與停止條件。
- 任務狀態與部署狀態的雙軌管理。
- 安全驗證、產生檔案驗證與資料異動驗證的分級。
- 核准驗證白名單、未知指令的預設處理及分類失效條件。
- 任務狀態轉換與各狀態更新哪些文件、更新順序及失敗回復方式。
- 新 session 啟動與交接規則。
- 專門流程優先於通用流程的導流規則。
- 工作區路徑、未提交變更及多 AI 寫入衝突保護。
- worktree 寫入鎖的取得、續期、釋放與殘留處理。

### 3.4 `TASK_TEMPLATE_任務模板.md`

用途：在動工前建立可供使用者核准的任務卡。

固定欄位：

- Task ID、任務卡版本與建立日期。
- Task 名稱。
- 問題類型。
- 背景。
- 已確認的產品決策。
- 目標。
- Scope。
- Non-scope。
- 安全限制。
- 預計影響的頁面、API、資料流、元件或文件。
- 驗證方式與完成定義。
- 資料保護與回復方式。
- Git 授權範圍，包括是否允許建立 branch 或 local commit。
- 風險與待決問題。
- Scope 核准狀態、核准者、核准日期、核准原文摘要與核准版本。

此模板屬於動工前文件，不取代完成後的 Summary。

任務卡存放於 `docs/implementation/tasks/`，使用穩定檔名 `Txx-英文名稱_中文名稱.md`。Scope 版本與變更紀錄寫在文件內，不為每次小修正建立新檔。若核准後擴大 Scope，新增 Scope 版本並重新取得核准，原核准紀錄不得覆蓋。

### 3.5 `HANDOFF_TEMPLATE_新對話交接模板.md`

用途：在任務切換、階段完成或對話過長時，產生乾淨的新 session 交接資料。

固定欄位：

- 目前 branch、commit 與部署狀態。
- 專案正式路徑及工作區是否已核對。
- 本輪完成項目及驗證結果。
- 尚未完成、阻塞或尚未人工驗收的項目。
- 已拍板且不可重新推翻的產品決策。
- 當前 Scope、Non-scope 與高風險限制。
- 下一個建議任務。
- 新 AI 必須讀取的最小文件清單。
- 可直接貼到新對話的開場文字。

交接摘要由目前狀態與任務 Summary 組合而成，不成為另一份長期狀態來源。

交接內容預設產生為可貼入新對話的文字，不強制建立永久檔案。只有使用者要求保存或任務跨多人交接時，才存入 `docs/implementation/handoffs/`，使用日期與任務 ID 命名；交接完成後仍以 `CURRENT_STATE_目前專案狀態.md` 為目前狀態入口。

### 3.6 `ROADMAP_產品路線圖.md`

用途：保存有價值但不應立即插隊的產品想法。

分類：

- 現在必做。
- 下一階段。
- 長期 Roadmap。
- 暫時記錄，不做。
- 併入既有模組。
- 應獨立成新模組。

每筆項目至少記錄名稱、來源、價值、暫不執行原因、啟動條件、依賴項與相關規格連結。Roadmap 不複製完整需求，也不代表已取得實作核准。

### 3.7 `docs/sop/`

用途：將重複踩坑與固定檢查方式轉成可重用流程。

起始結構：

- `README_SOP索引.md`
- `PRODUCTION_DEPLOYMENT_正式環境部署檢查.md`
- `LOCAL_VERIFICATION_本機驗證與快取排查.md`
- `AUTOMATED_VERIFICATION_自動驗證安全分級.md`
- `AI_VERIFICATION_POLICY_自動驗證政策.json`
- `CHINESE_ENCODING_中文編碼與亂碼處理.md`

既有的 `規格書修改流程.md`、`規格書文件修正原則.md`、`engineering-data-model-spec/schema修改流程.md` 與 `engineering-data-model-spec/schema修正原則.md` 保留原位。SOP 索引只連結到它們，不重新抄寫。

SOP 與治理入口屬於持續更新文件，檔名不加日期，文件內記錄最後更新日期與變更摘要。測試腳本、Summary、設計規格及必要的歷史交接檔則繼續使用版本或日期保存證據。

`AI_VERIFICATION_POLICY_自動驗證政策.json` 是機器可讀的正式驗證白名單；Markdown SOP 負責向使用者解釋規則，JSON 負責讓 AI 依明確資料判定，不得由 AI 只靠測試名稱自行認證。

## 4. 三層操作權限

### 4.1 第一層：可以自動執行，完成後回報

適用於低風險、唯讀，或已列入核准驗證白名單的無副作用操作，例如：

- 讀取檔案。
- 搜尋程式碼與文件。
- 檢查 branch、Git status、diff 與 log。
- 盤點專案結構。
- 執行型別檢查與 lint。
- 執行 `AI_VERIFICATION_POLICY_自動驗證政策.json` 明確標記為 `readonly` 且分類仍有效的測試。
- 讀取本機驗證輸出。

AI 不需要為這些操作逐項詢問。若工具平台本身要求權限核准，仍須遵守平台安全機制。

「無副作用」不得由執行中的 AI 臨時自行認證。只有驗證白名單中已記錄核准者、核准日期、指令、入口檔案與副作用分類的項目，才可進入第一層。未列入、資料不完整、分類過期或白名單檢查失敗的指令，一律視為 `unclassified`，不得自動執行。

測試檔名可採 `*.readonly.test.*` 等慣例協助辨識，但檔名不構成授權。若 package script、測試入口檔或白名單列管的副作用相關檔案被修改，原分類立即失效，必須重新提出分類與核准；AI 不得自行更新核准欄位。

讀取檔案不包含任意輸出機密內容。AI 優先讀取 `.env.example`；只有任務確實需要時才能讀取 `.env`，且不得在回報、Summary、log 或對話中顯示密碼、Token、金鑰及完整連線字串。

### 4.2 第二層：可以先做，但必須回報

適用於不直接改變產品行為或正式資料、但會影響下一步決策的工作，例如：

- 技術分析與根因調查。
- 提出檔案修改計畫。
- 列出風險、替代方案與取捨。
- 設計資料流與 UI flow。
- 建立 Discovery 結論。
- 規劃測試、驗收與回復方式。
- 建立或更新任務卡草稿、Roadmap 記錄及 `CURRENT_STATE_目前專案狀態.md` 中可驗證的事實。
- 在沒有共用 dev server，或使用隔離輸出目錄的前提下執行 build；若可能干擾使用者測試，先回報再執行。
- 執行白名單標記為 `isolated-stateful`，且已核對隔離資料庫識別、禁止連到共用／正式資料庫及清理方式的測試；完成後回報隔離方式與清理結果。

AI 可先完成方案，再把需要使用者拍板的決策集中回報。

第二層只允許更新治理草稿、狀態事實或隔離測試環境，不等於取得產品程式、正式規格、共用開發資料或正式環境的修改權。

### 4.3 第三層：必須先確認

包含高風險、難以回復或會影響正式狀態的操作：

- 修改 Prisma schema 或其他正式資料模型。
- 建立或執行 migration。
- 刪除資料或批次修改資料。
- 修改權限模型、登入安全或正式環境設定。
- 執行 `db:seed`、`db:push`，或任何會重設、覆蓋、建立、更新、刪除共用開發資料的指令。
- 對共用本機資料庫執行會新增、更新或刪除資料的 smoke test。
- push main 或其他遠端分支。
- 部署 Preview 或 Production。
- 執行正式環境操作。
- 安裝新套件或引入新的外部服務，若會改變專案依賴或成本。
- 建立、切換或刪除 branch，以及執行 `git add` 或 `git commit`，除非核准任務卡已明確授權。
- 丟棄未提交變更、重寫 Git 歷史、force push 或執行破壞性 Git 操作。
- 刪除、搬移或大批改名檔案，除非已明確列入核准 Scope。
- 修改 `AGENTS.md`、`AI_WORKFLOW_AI協作流程.md` 或其他核心治理規則；`CURRENT_STATE` 的事實更新與已核准任務紀錄除外。
- 超出已核准 Scope 的程式、文件或產品行為修改。

遇到上述事項時，AI 必須說明原因、影響、風險及建議方案，等待使用者確認。

### 4.4 驗證白名單的機器判定

`AI_VERIFICATION_POLICY_自動驗證政策.json` 每筆指令至少包含：

- `command`：允許執行的完整指令，不接受模糊前綴。
- `classification`：`readonly`、`generated-output`、`isolated-stateful`、`shared-stateful` 或 `unclassified`。
- `entryFiles`：package script 與測試入口檔。
- `writes`：可能寫入的檔案、資料夾或資料庫；沒有時明確使用空陣列。
- `databaseTarget`：`none`、`isolated-test`、`shared-local`、`preview` 或 `production`。
- `requiresDevServer` 與 `requiresNoDevServer`。
- `requiresConfirmation`。
- `approvedBy`、`approvedAt` 與 `approvalReference`。
- `fingerprints`：列管入口與副作用相關檔案的雜湊；不一致時分類失效。

AI 執行前必須確認完整指令相符、分類允許、必要欄位齊全、fingerprint 相符、資料庫目標及 dev server 條件成立。任一項無法證明就停止自動執行，將指令降級為 `unclassified` 並回報。

修改驗證白名單、核准欄位或 fingerprint 屬於核心治理變更，必須先取得使用者確認。AI 可以先產出建議分類與差異，但不能自行把建議寫成已核准狀態。

## 5. Scope 核准前後的行動規則

### 5.1 Scope 尚未核准

AI 只能進行第一層與第二層工作，不得修改一般程式碼、正式產品／schema 文件、產品行為、共用資料或正式環境。

AI 可以把 Discovery、任務卡草稿、Roadmap 記錄及可驗證的目前狀態寫入治理文件，寫入後需回報。這是治理紀錄例外，不代表產品 Scope 已核准。

只有使用者在對話中明確批准，或任務卡已記錄可追溯的既有批准，才可標示為 `已核准`。AI 不可從模糊語句、Roadmap 優先級或過往相似任務推定批准。新 session 若找不到核准版本與證據，狀態一律視為 `待核准`。

### 5.2 Scope 已核准

AI 可在核准範圍內：

- 修改一般程式碼。
- 修改任務範圍內的一般文件。
- 新增或更新測試。
- 修正因本任務造成或阻塞本任務的 lint、型別與 build 錯誤。
- 執行必要驗證。
- 建立或更新本任務適用的測試腳本／文件審閱清單與 Summary。
- 更新任務索引與 `CURRENT_STATE_目前專案狀態.md` 中的任務狀態。

AI 不需要每改一個檔案便重新詢問。完成後集中回報修改內容、驗證結果、未完成事項與待使用者人工驗收項目。

若實作中發現必須超出 Scope 或觸及第三層操作，立即停止相關部分並請使用者確認；其他不受影響且仍位於 Scope 內的工作可繼續。

若 Scope 內容改變，必須先更新任務卡的 Scope 版本、列出新增與移除內容，並對變更部分重新取得核准；舊版本的核准不得自動延伸。

### 5.3 Worktree 寫入鎖

任何 AI 在第一次寫入檔案前，都必須以不可覆蓋、具原子性的方式建立專案根目錄下的 `.ai-worktree-lock.json`。此檔加入 `.gitignore`，不納入 commit。

寫入鎖至少記錄：

- AI 或 session 識別。
- Task ID 與 Scope 版本。
- worktree 正式路徑。
- 預計修改的檔案或目錄範圍。
- 建立時間、最後續期時間與時區。
- 執行狀態及交接資訊。

規則如下：

1. 唯讀分析不需要取得寫入鎖。
2. 建立 lock 必須使用「不存在才建立」的原子操作，不可先讀取後直接覆蓋。
3. 已存在其他 session 的 lock 時，不得進行任何寫入；可以繼續唯讀分析或改用獨立 worktree。
4. 長時間任務需更新最後續期時間，但續期只能由相同 session 執行。
5. 任務完成、明確阻塞或交接完成後，在最後一次更新 `CURRENT_STATE` 之後釋放 lock。
6. lock 超時、session 消失或疑似殘留時，AI 不得自行刪除或接管；必須回報使用者確認。
7. lock 只能防止遵守治理流程的 AI 互相衝突，不能阻止一般編輯器或未遵守規則的工具，因此仍須配合 Git status 與重疊檔案檢查。

## 6. 任務狀態與部署狀態

### 6.1 任務生命週期

任務狀態只描述工作本身，不包含部署狀態：

1. `Discovery`：問題與根因尚在分析。
2. `待核准`：任務卡已完成，等待 Scope 決策。
3. `已核准`：使用者已批准指定 Scope 版本，可以動工。
4. `實作中`：一般程式碼、文件及測試正在修改。
5. `自動驗證通過`：AI 已完成必要檢查，但尚未等同產品完成。
6. `待人工驗收`：使用者需依測試腳本或文件審閱清單驗證。
7. `完成`：適用的人工驗收或文件審閱已通過，Summary 已定稿，狀態已收尾。
8. `阻塞`：存在明確外部依賴或需要使用者決策，暫時無法繼續。
9. `取消`：使用者決定不再執行，需記錄原因。
10. `已被取代`：需求由另一任務或新版 Scope 接手，需連結取代項目。

### 6.2 部署狀態

部署狀態獨立記錄，不視為任務生命週期的下一步：

- `不適用`：文件或不需部署的任務。
- `未部署`。
- `Preview 已部署，未驗證`。
- `Preview 已驗證`。
- `Production 已部署，未驗證`。
- `Production 已驗證`。
- `已回復`：部署已撤回或回復至舊版本。
- `未知`：無法查證時使用，不可自行推定。

「完成」不等同「已部署」，「已部署」也不代表人工驗收通過。本機、Preview 與 Production 必須分開記錄。

## 7. 文件更新責任

| 事件 | 任務索引 | Summary | `CURRENT_STATE_目前專案狀態.md` |
|---|---|---|---|
| 建立新任務草稿 | 新增草稿任務與初始狀態 | 不建立 | 指向目前任務並標示未核准 |
| Scope 核准 | 更新為已核准 | 不建立 | 記錄核准版本與證據 |
| 實作進行中 | 必要時更新狀態 | 不建立或只留草稿 | 更新工作狀態與阻塞 |
| 自動驗證完成 | 更新為待人工驗收 | 建立摘要草稿 | 記錄驗證結果 |
| 人工驗收通過 | 更新為完成並連結 Summary | 定稿 | 移除進行中項目並填寫下一步 |
| 部署狀態改變 | 更新部署欄位 | 必要時補記部署驗證 | 記錄實際環境與查證時間 |
| 阻塞、取消或已被取代 | 更新原因與相關任務 | 建立或更新摘要，記錄未完成內容 | 記錄阻塞／結束原因與下一步 |
| 修正歷史錯誤 | 必要時修正 | 只修正錯誤部分 | 通常不涉及 |

每個程式碼小修改不需要同步更新三處。只有狀態轉換或任務收尾時才更新對應文件。

狀態收尾的更新順序固定為：先完成 Summary 草稿，再更新任務索引，最後更新 `CURRENT_STATE_目前專案狀態.md`。如此可避免目前狀態指向尚未存在的摘要。任一步失敗時，需在目前狀態標示不一致，不得假裝全部完成。

## 11. 驗證與錯誤處理

- 驗證前先判斷指令會不會寫入 `.next`、啟停 dev server、修改 SQLite、呼叫外部服務或改變正式狀態。
- 型別檢查、lint 與確認無副作用的唯讀測試可自動執行。
- build 會產生 `.next`；只有在不干擾使用者共用 dev server，或使用隔離輸出時才可直接執行，並記錄執行條件。
- 會寫資料的測試只能在明確隔離的測試資料庫自動執行；若使用共用 `dev.db`，必須先確認。
- `db:seed`、`db:push`、migration 與正式環境測試不屬於自動驗證。
- AI 必須區分未執行、失敗、通過與無法確認，不得把未驗證描述成完成。
- 驗證失敗時，先診斷根因；修正若仍在核准 Scope 內可直接處理，超出 Scope 或觸及高風險操作則停下確認。
- 正式站未更新時，優先依部署 SOP 檢查 branch、commit、deployment 與 domain 指向，不先假設程式錯誤。
- 中文文件需使用 UTF-8 與繁體中文，交付前檢查亂碼、`??` 及替代字元。

### 11.1 Windows dev server 與 build 前置檢查

執行會寫入 `.next` 的 build 前，AI 必須：

1. 從 `CURRENT_STATE_目前專案狀態.md`、package script 或本輪啟動紀錄取得預期 port；不得只假設一定是 3000。
2. 使用 `Get-NetTCPConnection`；若不可用，再使用 `netstat -ano`，檢查該 port 是否處於監聽狀態。
3. 依 PID 檢查程序是否為 Node／Next，並盡可能核對命令列與專案目錄。
4. 檢查本 session 是否啟動過 dev server，以及是否有其他 session 的 worktree lock 或執行紀錄。
5. 若偵測到本專案 dev server、無法確認程序所有者、沒有權限查看程序，或目前狀態顯示使用者正在測試，均視為「存在共用 dev server」。

存在或無法排除共用 dev server 時，AI 不得自動執行共用 `.next` 的 build、停止程序或刪除 `.next`；必須先回報。只有確認沒有共用 dev server，或在獨立 worktree／獨立輸出目錄完成隔離，才可依白名單分級執行。

人工驗收依任務類型分流：

- 使用者可見、後台可見、資料流程或登入權限變更：必須建立或更新帶版本與日期的人工測試腳本。
- 純治理、純文件或不影響執行行為的任務：使用文件審閱清單即可，不強制建立網站操作測試腳本。
- 純內部程式重構：若外部行為不變，可使用自動驗證加回歸檢查；若有任何使用者流程風險，仍需人工測試腳本。
