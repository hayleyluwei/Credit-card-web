## 背景

2026-07-27 使用者詢問：「要怎樣設定排程，讓 AI（Claude Code／Codex）固定去讀取官網資料，然後自動批次更新資料寫入資料庫？」

同日的討論釐清了一個重要現實：**完整的「固定讀官網 → 自動直接寫進資料庫、中間無人審核」形態不建議實作**，原因有三：

1. **抓取本身不可靠且會靜默失敗**：T17 資料抽查時，國泰 CUBE 卡官網（`cathaybk.com.tw…CUBE_rights`）以純 HTTP 抓取讀到的是 2024 舊版內容，因為現行 2026 內容是 JavaScript 動態載入；使用者以真人瀏覽器確認才是 2026 版。銀行官網普遍使用 JS 渲染、改版、擋機器人與 PDF 公告，排程程式抓錯時不會自知，仍會照樣寫入。
2. **與既有治理與資料正確性機制衝突**：`scripts/import-offer-data.mjs` 與 `scripts/verify-release-data.mjs` 都把「查證日期（`lastVerifiedAt`）」「來源網址（`sourceUrl`）」列為**必填、缺了就擋下不寫**，這是刻意設計成需要人看過官方頁面。規格書 v3（`DATA_COLLECTION_SPEC…-v3-2026-07-27.md`）的「情況一 vs 情況二」判斷（延展沿用代號 vs 換新代號）、多層回饋拆解、術語白話原則，都需要人腦判斷。`T18` 任務卡 Non-scope 明文寫「不建立自動爬蟲、排程匯入」；schema 刻意排除 `CrawlSource`／`ImportJob` model，且 `scripts/verify-t02-prisma.mjs` 有測試守著不准它們被加回。
3. **財務資料錯誤後果嚴重**：驗收規則把「回饋數字錯誤」列為重大錯誤；自動抓取＋自動發布等於讓可能抓錯的程式把錯誤回饋率直接秀給使用者、還被 AI 引用。

因此本任務的方向是**半自動**：排程只做「不需要判斷」的苦工（抓取＋比對＋產出差異草稿），最後仍由人工核准才寫入資料庫。此設計剛好接上使用者本次已建立的增量匯入模式與規格書 v3 判斷規則。

相關文件：

- 資料規格：`docs/data-collection/DATA_COLLECTION_SPEC_信用卡優惠資料蒐集與分類規格書-v3-2026-07-27.md`（3.4 情況一/二判斷、6.6 官方數字照抄、查證日期必填）
- 部署與資料庫：`docs/implementation/tasks/T18-FIRST_RELEASE_DEPLOYMENT_第一版部署上線.md`（正式資料庫為 Neon PostgreSQL；本機為 SQLite）
- 條件結構化：`docs/implementation/tasks/T21-CONDITION_SCHEMA_優惠條件結構化規劃.md`（RewardTier 結構化後才利於「自動比對數字有沒有變」）

## 已確認決策

以下為 2026-07-27 討論中使用者與本 session 達成、本任務不重新討論的方向（仍待正式核准 Scope 才可實作）：

- **只做半自動，不做全自動寫入**：排程負責抓取＋比對＋產出差異報告，最後由人工核准才執行匯入。不建立「抓取即發布」的無人審核路徑。
- **人工核准閘門沿用既有機制**：核准後的寫入動作沿用本次已完成的 `npm run data:import` 增量 upsert 模式；判斷「延展沿用代號 vs 換新代號」沿用規格書 v3 的情況一/二規則。
- **排序在 T18 之後**：本機 SQLite（`prisma/dev.db`）只有本機摸得到，任何雲端排程現階段都寫不進去；等 T18 讓資料庫上 Neon PostgreSQL 後，雲端排程才有寫入對象。因此本任務天生排在 T18 上線之後（亦晚於 T21 條件結構化，結構化後自動比對才可靠）。
- **抓取層需能執行 JavaScript**：優先採用真瀏覽器渲染（如 Playwright／headless 瀏覽器）而非純讀 HTML，以避免 CUBE 那種讀到舊版的問題。

## 目標

在不繞過既有「官方來源＋查證日期＋人工核准」機制的前提下，讓排程自動承擔「定期檢查每筆優惠的官方來源頁是否有變動、並產出可供人工快速判讀的差異草稿」這段重複勞動，使人工只需針對「疑似有變」的少數優惠做確認與匯入，而非每輪盲目重讀全部資料。

## Scope v1（規劃內容；核准實作前不得執行）

若後續拍板通過，預期實作範圍包含：

- **抓取層**：新增一個可設定的抓取模組，讀取資料庫（或設定檔）中每筆優惠的 `sourceUrl`，以能執行 JavaScript 的方式取得官方頁面現況內容。需評估並於 Scope 核准時決定所採套件（如 Playwright），此為第三層「新套件」操作。
- **比對層**：把抓取到的官方頁面內容與資料庫現有欄位（回饋數值、上限、活動期間、條件文字）做差異偵測，輸出「哪幾筆疑似有變、變在哪」的結構化差異報告。**此層唯讀，不寫資料庫。**
- **報告與通知層**：差異報告以人可讀形式產出（檔案／PR／通知），並明確標示每筆疑似變動對應規格書 v3 的「情況一（延展）」或「情況二（換新代號）」建議，供人工判讀。
- **人工核准閘門**：人工看過差異報告、確認數字與情況判斷後，才由人（或人明確授權下）更新 xlsx 來源並執行 `npm run data:import`。排程本身**不得**自動跑寫入。
- **排程機制**：依待決問題 (a) 選定的機制（Windows 工作排程器／GitHub Actions／Claude Code 雲端 routine 之一）設定定期觸發抓取＋比對＋報告；不含自動匯入。
- **文件**：建立 T22 Summary、對應人工測試腳本或審閱清單、更新任務索引與 CURRENT_STATE；視需要升版規格書說明排程輔助流程。

## Non-scope

- **不做全自動寫入資料庫**：排程不得在無人核准下執行 `data:import`／`data:import:reset`／`db:seed`／`db:push` 或任何寫入。
- **不繞過查證日期與官方來源機制**：抓取結果不得自動填入 `lastVerifiedAt`／`sourceUrl` 當作「已查證」；查證仍以人工確認為準。
- **不重新啟用 `CrawlSource`／`ImportJob` schema model**，除非另行走 schema 專門流程與核准（本卡不含 schema 變更）。
- **不修改 Prisma schema、不建立 migration、不修改前後台產品程式碼**（抓取／比對為獨立腳本，不動產品行為）。
- **不做全站監控、錯誤追蹤平台導入**（Roadmap 另列）。
- **不接觸正式環境部署本身**（部署屬 T18）；本任務假設 T18 已完成、資料庫已在 Neon。
- **本任務卡本身只是規劃文件**，唯一交付物為這份 Markdown；不新增套件、不設排程、不寫資料。
- 不接觸正式環境、不部署、不執行 `git add`／commit／push（除非核准時另行授權）。

## 風險與待決問題

以下為尚未拍板的分岔路，任一項未決定前不應核准 Scope 進入實作：

1. **(a) 排程機制選哪個？** 三個選項各有硬限制（關鍵在「排程程式跑在哪、碰不碰得到資料庫」）：
   - **Windows 工作排程器**（跑在使用者本機）：現階段唯一能直接寫本機 SQLite `dev.db` 的，但只有電腦開機時會跑。
   - **GitHub Actions 排程 workflow**（跑在 GitHub 雲端）：碰不到本機 dev.db，但很適合「自動抓取＋比對後開一個差異報告 PR」給人審。
   - **Claude Code 雲端 routine（/schedule）**（跑在 Anthropic 雲端）：碰不到本機 dev.db，需等 T18 資料庫上 Neon 後、對正式資料庫才有意義。
2. **(b) 抓取由誰／用什麼執行？** 選項：LLM agent（Claude／Codex，較能理解頁面但有 API 成本與 session 需求）／確定性爬蟲腳本（較省成本但每家銀行要維護選擇器、改版即壞）／混合。需與 (a) 一併決定。
3. **(c) 排程頻率？** 信用卡權益多為每半年／每季改版；過度頻繁抓取徒增被擋風險與成本。需訂合理頻率（如每月一次或每季一次）。
4. **(d) 比對層在 T21 之前還是之後做？** 條件結構化（T21）完成後，回饋數字是結構化欄位，自動比對「數字有沒有變」較可靠；在 T21 之前只能對散文做較粗略的文字差異。建議排在 T21 之後，待確認。
5. **(e) 抓取到疑似變動時，草稿是否自動改 xlsx／開 PR，還是只產報告讓人自己改？** 影響人工核准閘門的自動化程度與風險。

次要待記錄事項：
- 各銀行官網服務條款與抓取頻率限制需逐一確認，避免違反使用條款或觸發封鎖。
- 抓取層需處理 JS 渲染、頁面改版、PDF 公告等多種來源型態，維護成本不低，需在 Scope 核准時評估投入是否划算（相對於維持人工＋增量匯入）。
