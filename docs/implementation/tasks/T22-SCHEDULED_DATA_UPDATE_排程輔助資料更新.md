## 背景

2026-07-27 使用者詢問：「要怎樣設定排程，讓 AI（Claude Code／Codex）固定去讀取官網資料，然後自動批次更新資料寫入資料庫？」

同日的討論釐清了一個重要現實：**完整的「固定讀官網 → 自動直接寫進資料庫、中間無人審核」形態不建議實作**，原因有三：

1. **抓取本身不可靠且會靜默失敗**：T17 資料抽查時，國泰 CUBE 卡官網（`cathaybk.com.tw…CUBE_rights`）以純 HTTP 抓取讀到的是 2024 舊版內容，因為現行 2026 內容是 JavaScript 動態載入；使用者以真人瀏覽器確認才是 2026 版。銀行官網普遍使用 JS 渲染、改版、擋機器人與 PDF 公告，排程程式抓錯時不會自知，仍會照樣寫入。
2. **與既有治理與資料正確性機制衝突**：`scripts/import-offer-data.mjs` 與 `scripts/verify-release-data.mjs` 都把「查證日期（`lastVerifiedAt`）」「來源網址（`sourceUrl`）」列為**必填、缺了就擋下不寫**，這是刻意設計成需要人看過官方頁面。規格書的「情況一 vs 情況二」判斷（延展沿用代號 vs 換新代號）、多層回饋拆解、術語白話原則，都需要人腦判斷。`T18` 任務卡 Non-scope 明文寫「不建立自動爬蟲、排程匯入」；schema 刻意排除 `CrawlSource`／`ImportJob` model，且 `scripts/verify-t02-prisma.mjs` 有測試守著不准它們被加回。
3. **財務資料錯誤後果嚴重**：驗收規則把「回饋數字錯誤」列為重大錯誤；自動抓取＋自動發布等於讓可能抓錯的程式把錯誤回饋率直接秀給使用者、還被 AI 引用。

**2026-08-05 進一步釐清了本任務真正的價值所在**。討論中使用者提出：「我不能像現在一樣，直接問你，你更新 xls 再去同步資料庫嗎？」——答案是**可以，而且現在就是這樣做的**（2026-08-04 補新卡即為此流程）。由此區分出兩件事：

- **執行**（查證官網、更新 xlsx、同步資料庫）：**現有人工流程已能完成，不需要 T22。**
- **偵測**（哪一筆優惠的官網悄悄改了）：**這才是缺口。** 使用者要能「來問 AI」，前提是已經知道有東西要改；但銀行不會通知，回饋率調降、活動延期、新增優惠都不會有人告知，網站就會一直顯示舊資料。**你不知道的事，你不會來問。**

因此瘦身版聚焦於「偵測 ＋ 通知」，把「執行」交還給已被驗證可行的人工流程。

相關文件：
- 匯入管線：`scripts/import-offer-data.mjs`（增量 upsert 模式，2026-07-27 建立）、`scripts/verify-release-data.mjs`
- 資料規格：`docs/data-collection/DATA_COLLECTION_SPEC_信用卡優惠資料蒐集與分類規格書-v7-2026-08-04.md`（3.4 情況一/二判斷、3.5 多層回饋、6.6 官方數字照抄、查證日期必填）

- 條件結構化：`docs/implementation/tasks/T21-CONDITION_SCHEMA_優惠條件結構化規劃.md`（RewardTier 結構化後才利於「自動比對數字有沒有變」）

## 已確認決策

### A. 通用（瘦身版與完整版都適用）

- **只做半自動，不做全自動寫入**：排程負責抓取＋比對＋產出差異報告；不建立「抓取即發布」的無人審核路徑。
- **(a) 排程機制 = GitHub Actions（2026-08-05 拍板）**：抓取＋比對層跑在 GitHub Actions 排程 workflow（GitHub 雲端），不受使用者電腦開關機影響。**拍板時一併釐清一個原本卡片寫錯的前提**：`prisma/dev.db` 已於 T18 停用，`.env` 的 `DATABASE_URL` 現在不論本機或雲端執行都是連同一個正式站 Neon PostgreSQL，原本「本機排程才能碰到資料庫、雲端排程碰不到」的判斷基礎已不成立。**補充事實（2026-08-05 查證）**：本專案 GitHub repo `hayleyluwei/Credit-card-web` 為**公開（PUBLIC）**，公開 repo 的 GitHub Actions 標準執行環境免費且不限時數，本任務規模無費用問題。
- **抓取層需能執行 JavaScript**：優先採用真瀏覽器渲染（如 Playwright／headless 瀏覽器）而非純讀 HTML，以避免 CUBE 那種讀到舊版的問題。
- **(b) 抓取與判讀方式 = 確定性爬蟲腳本（2026-08-05 拍板）**：以 Playwright 渲染頁面，抽取邏輯採每家銀行維護的確定性規則（選擇器／文字比對），**不使用 LLM 判讀**，以避免 API 成本與額外金鑰管理。使用者在了解「改版即壞、且會靜默壞掉」的缺點後仍選擇此方案。（**成本參考**：2026-08-05 查證，若改用 LLM 判讀，以每月一次／30 個頁面估算約為每月 NT$7～36，金額不高；使用者仍選擇確定性爬蟲，另一考量是不必在 GitHub Secrets 多管理一把 API 金鑰。）
- **強制配套：抓取健康檢查（2026-08-05，隨 (b) 綁定，不可省略）**：因確定性爬蟲最危險的失敗模式是「規則失效 → 抽到空值 → 比對結果為『無變動』→ 使用者誤以為官網沒變」，實作必須能區分「確認沒變」與「根本沒抓到」：① 每個來源頁的抽取結果須有基本合理性檢查（如必要欄位不得為空、數值需可解析、頁面需含預期關鍵字）；② 檢查未通過時，該次執行必須**明確失敗並發 Telegram 通知**（例如「第 N 個來源抓取失敗，規則可能已失效」），**不得回報為「無變動」**；③ 報告須同時列出「本次成功抓取數／失敗數」，讓使用者一眼看出覆蓋率。
- **(c) 排程頻率 = 每月一次（2026-08-05 拍板）**：最慢一個月內可發現權益變動或新增活動；兼顧被銀行網站封鎖的風險、執行成本與通知疲勞。信用卡權益雖多為每半年／每季改版，但新增活動出現時機不固定，故不採每季。
- **(d) 比對層排序 = 因事實而解決（2026-08-05 確認，非拍板）**：T21 已於 2026-07-27 完成，回饋數字已結構化為 `RewardTier`，比對層必然在其後實作，可直接比對結構化欄位而非散文。
- **後台與 xlsx 的職責分工（2026-08-05 釐清）**：後台仍是下列資料的唯一入口，完全不受排程影響——攻略文章（`Article`）、優惠行銷徽章（`badgeLabel`）、精選標記（`isFeatured`）、上下架開關（`isPublished`）、未來 T27 的首頁選讀內容。與 xlsx 重疊的核心資料（銀行／卡片／優惠內容、回饋數字、期間、RewardTier）則以 **xlsx 為權威版本**——後台對這類資料的手動修改屬暫時性，應回填 xlsx。

### B. 瘦身版專屬（現階段採用）

- **輸出只有 Telegram 通知，不產生 PR、不產生決策檔、不寫任何資料。**
- **收到通知後的處理方式 = 沿用現有人工流程**：使用者在對話中請 AI 依規格書實際查證官網來源 → 確認後更新 xlsx → 執行 `npm run data:import` 同步資料庫。此流程已於 2026-08-04 實際走過並驗證可行，不需要為它另建機制。
- **通知內容應足以讓使用者判斷要不要處理**：至少包含「哪幾筆優惠代號疑似有變」「變在哪（舊值 → 新值）」「官方來源網址」「本次成功／失敗抓取數」。
- **GitHub Secrets 只需要存放唯讀資料庫憑證**：瘦身版全程不寫資料庫，因此**不需要、也不應該**把具寫入權限的 `DATABASE_URL` 放進 GitHub Secrets。這一點大幅降低了 (a) 帶來的憑證暴露風險。

## 未來階段：完整版（已完成決策討論，現階段不實作）

> 以下內容為 2026-08-05 針對完整版逐項拍板的結果，**現階段不實作**，保留供未來網站開始營利、重新評估時直接沿用，不需重新討論。升級時屬 Scope 變更，需重新核准。

- **(e) 審閱流程 = Telegram 通知＋GitHub PR 逐筆決策（2026-08-05 拍板）**：① 發 Telegram 通知；② 使用者上 GitHub 打開 PR 審閱；③ 逐筆決定要不要採用；④ Merge 後才進入匯入。整批不要時直接 Close PR。
- **PR 內審閱對象必須是「文字格式決策檔」，不是 xlsx（技術現實所迫）**：`.xlsx` 對 GitHub 是二進位檔，PR 只會顯示 `Binary file not shown`，看不到任何逐筆差異，無法審閱。因此 PR 必須包含一份**人可讀、GitHub 可 diff 的文字檔**（CSV／YAML／Markdown 之一），每筆至少包含：優惠代號、疑似變動（舊值 → 新值）、官方來源網址、規格書 3.4 情況一／情況二建議、該筆自上次排程後是否曾被後台手動編輯過、以及一個可直接在 GitHub 網頁編輯的「決定」欄位。
- **逐筆決策方式 = 改「決定」欄位的值，不需要下任何指令**：把該筆的「決定」改成 `覆蓋` 或 `略過` 後 Merge；後續匯入只處理標記為 `覆蓋` 的列。實作上「略過」＝不把該列放進匯入批次即可，因為 `import-offer-data.mjs` 本身是增量 upsert、未列出的資料完全不會被動到。此設計刻意避免要求使用者打指令（通知情境預期是手機上操作）。
- **「決定」欄位預設值 = 一律預設「覆蓋」**：理由（使用者 2026-08-05 提出）：**「曾被後台改過」不等於「後台版本比較新、應該保留」**。實際時序常是——2 月排程更新 → 3 月使用者在後台手動修過某欄位 → 4 月排程又抓到官網有新活動，此時該欄位很可能**本來就該被新的官方內容覆蓋**。把後台編輯過的列預設成「略過」，等於假設後台版本永遠優先，這個假設在半年改版一次的信用卡權益情境下並不成立。因此「曾被後台改過」只作為**提醒標示**存在，不改變預設值。**已知殘留風險**：使用者若未讀完就 Merge，後台手動修改會被覆蓋且無第二道攔阻；該提醒標示是此設計下唯一的防線，不得省略。
- **後台手動編輯衝突偵測**：比對時檢查該筆資料的 `updatedAt` 是否新於「上次排程匯入時間」，若是則於報告與 PR 明確標示。（**瘦身版列為選配**：瘦身版所有異動都經使用者手動確認，此標示價值較低，但仍可作為輔助資訊。）
- **(f) Merge 後自動觸發匯入＝選項 B（2026-08-05 拍板）**：Merge 後由 GitHub Actions 自動執行 `npm run data:import`。**拍板時一併釐清一個重要認知**：Vercel 自動部署只處理程式碼，網站顯示的優惠／卡片資料是即時查 Neon PostgreSQL 而來，**不隨部署更新**；Merge 本身只是 repo 多一份檔案，必須有匯入動作才會改變網站內容。此決策使「Merge 鈕＝直接寫正式站」。
- **(g) 啟用自動匯入的兩項硬性安全前提（2026-08-05 拍板）**：下列兩項**未完成並驗證前，不得啟用 (f) 的自動匯入**：
  - **① 真正的備份／還原能力**：現行 `import-offer-data.mjs` 匯入前備份的是已停用的 `prisma/dev.db`（SQLite 殘留檔），對正式站 Postgres 毫無保護作用，屬「看似有備份、實際沒有」的假保護，須一併修正。做法擇一或並行：讓匯入流程對 Postgres 做真備份（如 `pg_dump`），或確認 Neon 方案的還原視窗並**實際演練過一次還原**（僅閱讀文件不算通過；Neon 免費方案的實際保留時間需登入主控台查證，本卡不臆測）。
  - **② 唯讀憑證分離**：於 Neon 另建唯讀資料庫使用者供抓取／比對層使用，僅匯入步驟使用具寫入權限的憑證。（**成本查證，2026-08-05**：在同一個 Neon 資料庫內多開一個權限受限帳號是 PostgreSQL 內建功能，不佔額外儲存或運算，**不需額外費用**；唯 Neon 免費方案可開幾個 role 需登入主控台確認。）
  - **③ 獨立開發資料庫：不列為前置條件**（使用者 2026-08-05 決定）。理由：屬專案長期基礎建設問題，若設為前置會使 T22 長期卡住；但此風險本身仍然存在，維持記錄於 `CURRENT_STATE_目前專案狀態.md`。
- **完整版的機密處理規則**：自動匯入跑在 GitHub Actions，因此**具寫入權限的 `DATABASE_URL` 必須存入 GitHub Secrets**，使正式站寫入憑證的存放位置從兩處（本機 `.env`、Vercel）增為三處。連線字串含資料庫帳號與明碼密碼，取得者可完整讀取、修改、刪除正式站全部資料，**GitHub 帳號安全性自此等同資料庫安全性**。規則：① 憑證由使用者本人直接貼入 GitHub Secrets 設定頁，**不得貼在對話中、不得寫入 repo 任何檔案**；② GitHub 帳號應啟用兩步驟驗證（2FA）；③ 抓取／比對層改用唯讀憑證後，寫入憑證只出現在匯入步驟；④ 若憑證曾暴露於較高風險情境，應立即於 Neon 輪替（rotate）密碼並同步更新三處設定。

## 目標

**（瘦身版）** 讓排程每月自動檢查每筆優惠的官方來源頁是否有變動，並在偵測到疑似變動或抓取失效時主動以 Telegram 通知使用者，使「官網悄悄改了但沒人發現」這個目前完全沒有防線的缺口被補上；實際的查證與資料更新仍由既有人工流程處理。

## Scope v2（瘦身版；核准實作前不得執行）

若核准通過，預期實作範圍包含：

- **抓取層**：新增一個可設定的抓取模組，讀取資料庫中每筆優惠的 `sourceUrl`，以 Playwright 等能執行 JavaScript 的方式取得官方頁面現況內容。抽取邏輯依 (b) 採確定性規則，每家銀行各自維護。新增瀏覽器渲染套件屬第三層「新套件」操作，實作前需再確認。
- **抓取健康檢查層**：對每個來源的抽取結果做合理性檢查，區分「確認沒變」與「根本沒抓到」；檢查未通過時明確失敗並發通知，報告須列出成功／失敗數。詳見「已確認決策」。
- **比對層**：把抓取到的官方頁面內容與資料庫現有欄位（`RewardTier` 的回饋數值、上限、活動期間、條件文字）做差異偵測，輸出「哪幾筆疑似有變、變在哪」。**此層唯讀，不寫資料庫。**
- **通知層**：以 Telegram 發送通知，內容包含疑似變動清單（優惠代號／舊值 → 新值／官方來源網址）與本次成功／失敗抓取數；可視需要附上規格書 3.4「情況一／情況二」建議供判讀。**無變動時是否也發通知，實作時定案**（建議：無變動不發，但抓取失敗一定要發）。
- **排程設定**：GitHub Actions 排程 workflow，每月一次觸發抓取＋比對＋通知。
- **憑證設定**：GitHub Secrets 存放**唯讀**資料庫連線字串與 Telegram Bot 憑證，由使用者本人直接設定。
- **文件**：建立 T22 Summary、對應人工測試腳本或審閱清單、更新任務索引與 CURRENT_STATE。
