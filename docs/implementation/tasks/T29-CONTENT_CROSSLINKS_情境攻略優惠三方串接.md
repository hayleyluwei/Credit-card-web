# T29 情境／攻略／優惠三方串接

建立日期：2026-08-18（Asia/Taipei）
任務卡版本：v1.2（草案）
核准狀態：待核准（(b) 已拍板，其餘待決問題未定）
問題類型：UX 改善／內容架構

> **狀態說明**：本任務卡只記錄規劃內容，**不構成任何實作授權**。使用者正式核准 Scope 之前，不得修改任何前台頁面、元件或資料。本卡唯一交付物即這份 Markdown。

## 背景

T28 把首頁情境卡改成問句式標題（例如「繳稅金額大，回饋能省下多少？」「學費也可以刷卡拿回饋嗎？」「保費一次繳，怎麼刷才有感？」），語氣變親近了，但**落地頁沒有跟上**。

使用者於 2026-08-18 指出這個落差：**卡片承諾了一個答案，點進去卻只有一份優惠清單。** 清單回答不了「能省多少」「划算嗎」這類問題——那是攻略文章的守備範圍。

這個問題在「帳單日常」那一組（繳稅／學費／水電瓦斯／保費）特別明顯：金額大、規則複雜、一年只做幾次，使用者要的是**結論**而不是**選項**。

同時，使用者也指出反方向的缺口：**攻略文章讀完之後應該能導回具體的優惠**——回到該情境的優惠列表，或直接導到特定卡片的優惠頁。目前攻略文章是內容的終點，不是行動的起點。

使用者於同日進一步指出第三個缺口：**優惠頁看不到自己的情境標籤**——查繳稅優惠時，明明有掛繳稅標籤的優惠，點進去卻只顯示「現金回饋」，沒有任何回到繳稅情境的入口。

因此本任務處理的是**情境、攻略、優惠三者互相到達**，不只是單向加連結。

### 目前已具備的基礎（不需重做）

- T20 已建立 `/guides`、`/guides/[slug]`、`Article` model 與後台 CRUD。
- 情境頁（`/scenarios/[slug]`）已有「slug 相同即視為對應攻略文」的關聯機制，找到文章時會顯示「延伸閱讀」區塊。
- T28 已建立 `SCENARIO_COPY` 對照表（`src/lib/domain-scenario-copy.ts`），情境卡的標題與行動文字集中管理。
- 攻略文章內文為 Markdown，已支援連結、表格與 callout 樣式。

### 真正的缺口

1. 首頁情境卡不論有無攻略文章，行動文字一律是「查看優惠」，指向情境頁。
2. 攻略文章沒有制度化的「導回優惠」出口，只能靠作者在 Markdown 裡自己寫連結。
3. 優惠頁不顯示情境標籤，也沒有連回情境頁的入口；標籤只存在於 JSON-LD，人看不到（詳見 Scope D）。
4. **目前 0 篇已發布文章**，所以缺口 1、2 的連結改動在有文章之前都不會產生可見效果（缺口 3 不受此限，可獨立生效）。

## 已確認決策

- 本任務**不重新設計視覺**；一律沿用 T28 已定案的卡片生活誌風格契約。
- 不得產生死連結：沒有對應文章時必須自動退回現有行為。

### 2026-08-18 使用者拍板：文章導回優惠採「自動為主、手動優先」

**規則：預設自動依標籤撈取；若該篇文章有明確指定的導回目標，則以明確指定為準、覆蓋自動結果。**

這是刻意的雙軌設計，兩邊各自解決不同問題：

| | 自動（預設） | 手動指定（優先） |
|---|---|---|
| 來源 | 文章對應情境的標籤 | 作者於後台逐筆指定 |
| 優點 | 零維護；新增優惠自動納入 | 精準；可表達「我推薦這三筆」 |
| 適用 | 泛談某個情境的文章 | 有明確結論或排序的文章 |

**手動指定的目標可以是不同層級的連結**，由使用者的實例歸納：

| 使用者的例子 | 目標型態 |
|---|---|
| 文章談「CUBE 卡繳學費」→ 導到 `/offers/cathay-cube-private-school-tuition-2026` | **單一優惠** |
| 文章談「現金回饋」這個議題 → 導到 `/categories/cashback` | **分類** |
| 文章列「現金回饋前三名」→ 同時導到 `ctbc-linepay-rewards-2026h2`、`ctbc-uniopen-core-rewards-2026h2`、`taishin-jkopay-card-bill-payments-2026` | **多筆優惠，且順序有意義** |

因此手動指定必須支援：**多筆**、**混合型態**（優惠／分類，未來可能含卡片或情境）、**保留作者指定的順序**（「前三名」的名次不能被系統重排）。

上述五個網址已於 2026-08-18 實測皆回應 200，可作為實作與測試的真實案例。

## 目標

讓**情境、攻略文章、優惠**三者互相到達，形成走得完、回得來的路徑：

- 情境 → 攻略（Scope A）
- 攻略 → 優惠／分類／卡片（Scope B、C）
- **優惠 → 情境**（Scope D，2026-08-18 併入）

使問句式標題的承諾與落地頁實際提供的內容一致，並讓使用者從任一節點都能橫向探索，而不是每次退回首頁重新開始。

## Scope（規劃內容；核准實作前不得執行）

### A. 情境卡的行動文字隨內容自適應

| 情況 | 行動文字 | 連到 |
|---|---|---|
| 該情境**有**已發布攻略文章 | 例如「讀懂再決定」 | 攻略文章 |
| 該情境**沒有**文章 | 「查看優惠」（現況） | 情境頁 |

首頁需要知道每個情境有無對應文章，因此首頁查詢需增加一次文章 slug 的取得（僅取 slug 清單，不取全文）。

### B. 攻略文章導回優惠的制度化出口（雙軌：自動為主、手動優先）

依 2026-08-18 拍板：

1. **自動（預設）**：文章頁自動附上「相關優惠」區塊，依該文章對應情境的標籤撈取已發布優惠。作者不做任何設定就有基本效果，且新增優惠會自動納入。
2. **手動指定（覆蓋自動）**：`Article` 新增一個選填欄位，讓後台逐筆指定導回目標。有指定時完全取代自動結果，不混合顯示，避免作者精選的清單被自動撈的內容稀釋。

**手動指定需支援的能力**（見「已確認決策」的實例）：

- 多筆目標
- 混合型態：單一優惠（`/offers/...`）、分類（`/categories/...`），設計上保留卡片與情境的擴充空間
- **保留作者指定的順序**——「前三名」的名次由作者決定，系統不得重排

**這一項會改 schema**（新增 `Article` 選填欄位），須依 `AI_WORKFLOW` 走 schema 專門流程：先確認清單、備份、migration、同步 spec。

### C. 導回特定卡片的優惠

卡片詳情頁（`/cards/[slug]`）已有「這張卡的優惠」區塊，可直接作為落點。

實務上使用者的例子（「CUBE 卡繳學費」）其實**指向單一優惠而非整張卡**——因為那才是文章真正在談的東西。因此卡片層級的落點屬於 B 的手動指定所支援的型態之一，不需要另建機制；真正缺的是「某張卡 × 某個情境」這種交叉落點，但目前沒有對應 route，列為待決問題 (c)。

### D. 優惠頁顯示可點的情境標籤（2026-08-18 併入）

**起因**：使用者查繳稅優惠時發現 `taishin-jkopay-card-bill-payments-2026`（台新街口聯名卡繳稅費）「用繳稅查會找不到」。

**實測診斷結果——資料沒有問題，是呈現的問題**：

- 該優惠的標籤實際為 `繳稅,學費,水電瓦斯,行動支付,加碼,需登錄,期間限定`，**確實掛了繳稅**。
- `/scenarios/tax-payment` 有列出它、搜尋「繳稅」也找得到（2 筆），**兩條路徑都通**。
- 真正的缺口在**優惠頁本身**：麵包屑只呈現「首頁 / 現金回饋 / 標題」，標籤完全不顯示，連到情境頁的連結 0 個。標籤只存在於 JSON-LD 的 `keywords`——給搜尋引擎與 AI 讀的，**人看不到**。

**根本原因**：網站有兩套並行的分類軸——「分類」（6 種、每筆只能一個）與「情境標籤」（14 種、可多個）。這個雙軸設計本身正確（「什麼類型的回饋」與「能用在什麼場合」是兩件事），但目前只有分類軸在畫面上有存在感，情境軸在優惠頁是隱形的。

**做法**：優惠頁在摘要下方新增一列「這筆優惠可以用在」，列出該優惠的標籤。

**關鍵設計——兩種標籤必須外觀可辨**：

| 標籤 | 外觀 | 可點 | 連到 |
|---|---|---|---|
| 屬 14 個核心情境者（繳稅／學費／水電瓦斯…） | 淡藍底、深藍字、帶箭頭 | 是 | `/scenarios/[slug]` |
| 其餘標籤（行動支付／加碼／需登錄／期間限定…） | 灰底灰字、無箭頭 | 否 | 無對應頁面 |

**不得把所有標籤都做成連結**——非核心情境的標籤沒有對應頁面，全部可點會產生死連結，違反風格契約與本卡的既有原則。

**效果**：使用者從任一優惠都能橫向跳到相關情境，不必每次退回首頁；原本只在結構化資料裡的標籤也變成真實站內連結。

**與 2026-07-29 決定的關係（必須記錄，避免被誤認為走回頭路）**：當時移除優惠詳情頁的「優惠摘要」側欄，理由是「純文字重複顯示分類與標籤，未接結構化資料、對 SEO 與 AI 引用零效果」。本次讓標籤重新出現**方向看似相反，但性質不同**——當時是純文字，現在是**可點的導覽入口**，具備實際導覽功能。這是有意識的轉向，不是推翻。

## 風險與待決問題

1. **(a) 情境與文章的對應方式要不要沿用「slug 相同」？** 目前情境頁用這個慣例。優點是零設定；缺點是一個情境只能對應一篇文章，且文章 slug 被綁死（不利 SEO 命名彈性）。是否改為在後台明確指定對應關係？
2. ~~**(b) 文章導回優惠要用「自動依標籤撈取」還是「後台明確指定」？**~~ **已於 2026-08-18 拍板：兩者都要，自動為主、手動優先。** 詳見「已確認決策」與 Scope B。連帶確定**本任務會改 schema**（`Article` 新增選填欄位），須走 schema 專門流程。
3. **(c) 「某張卡 × 某個情境」的交叉落點要不要做？** 已釐清：單一優惠、分類、卡片這三種落點都由 (b) 的手動指定涵蓋，不需另建機制。真正缺的是「CUBE 卡在繳學費情境下的所有優惠」這種交叉頁面——目前沒有對應 route。**是否需要？** 若需要，等於新增 route（例如 `/cards/[slug]/scenarios/[scenario]`），會擴大 Scope 並影響 sitemap 與 SEO；若不需要，這類需求就用手動指定列出具體優惠來表達。
4. **(d) 情境卡的行動文字要怎麼寫？** 有文章時若寫「讀懂再決定」，與無文章時的「查看優惠」語氣不同，需確認使用者偏好；也要考慮 14 個情境是否一律相同文字。
5. **(e) 執行順序：先寫文章還是先改連結？** 在有文章之前，連結改動不會有可見效果。建議先寫第一篇（建議「繳稅」——問句最具體、現有優惠資料最多），再回頭做串接，否則無從驗證。
6. **(f) 與 T27 的關係**：T27 的「本月情境選讀」也是導向情境或文章的入口，兩者的連結規則應一致，避免同一個目的地有兩套不同的導向邏輯。
7. **(g) 手動指定的欄位格式怎麼設計？**（因 (b) 拍板而新增）需支援多筆、混合型態、保留順序。可能作法：存 JSON 陣列（如 `[{"type":"offer","slug":"..."},{"type":"category","slug":"..."}]`），或存路徑字串清單。前者結構清楚但後台輸入較繁瑣；後者輸入直覺但需驗證路徑是否存在、型態需由路徑推斷。**無論何者都必須在存檔時驗證目標真實存在**，否則會產生死連結——這正是 T28 的契約與本卡都明令禁止的。
8. **(h) 優惠頁的標籤列放哪裡、標題怎麼寫？**（Scope D）示意圖採「摘要下方、狀態徽章上方，以細線分隔，標題為『這筆優惠可以用在』」。位置與用字待確認；另需決定非核心標籤要顯示為灰色不可點，還是乾脆不顯示。

- v1.1／2026-08-18：使用者拍板 (b)：文章導回優惠採「自動依標籤撈為主、手動明確指定優先」雙軌制；並以三個實例釐清手動指定需支援多筆、混合型態（優惠／分類）、保留作者順序。連帶確定本任務會新增 `Article` 選填欄位＝改 schema。(c) 收斂為「是否需要卡片×情境的交叉 route」；新增 (g) 手動指定的欄位格式與存檔驗證。
- v1／2026-08-18：建立草案。起因為使用者檢視 T28 上線後的首頁情境卡，指出「問句式標題承諾了答案，落地頁卻只有優惠清單」的落差，並進一步要求攻略文章需能導回相關優惠與特定卡片，形成雙向串接。記錄現有基礎（T20 的文章功能與 slug 對應機制、T28 的 `SCENARIO_COPY`）、三項真正缺口與 6 個待決問題，待核准。
