# T27 首頁本月情境選讀模組

建立日期：2026-08-05（Asia/Taipei）  
任務卡版本：v2（草案）<br>
核准狀態：待核准  
問題類型：功能需求／資料模型／首頁資訊架構

> **狀態說明**：本任務卡只記錄規劃內容，**不構成任何實作授權**。在使用者針對「風險與待決問題」逐項拍板、正式核准 Scope 版本，並完成 schema 專門流程所需的修改清單確認前，不得修改 Prisma schema、建立 migration、讀寫資料庫、修改首頁或後台程式碼、部署或 push。

## 背景

使用者在「卡片生活誌」視覺原型中確認手機版首頁偏好保留「本月情境選讀」：它位於首頁主視覺後、熱門情境前，作為每月可替換的編輯推薦入口，例如連到旅行情境、攻略文章或一筆優惠詳情。

目前首頁已有熱門情境、優惠分類、信用卡、精選優惠與最新優惠，但沒有可由後台設定的首頁主題推薦模組。現有 `Article` model 可存放攻略文章，`SiteSetting` 只有網站名稱與列表數量等全站設定；兩者都沒有「本月情境選讀」的顯示內容、連結目標與上架排程欄位。因此若內容需要每月變更，不能以固定「去旅行」文案或寫死首頁程式碼處理。

相關任務：

- T20：攻略文章功能與自動情境頁（已完成）。T27 可連結既有情境頁或文章，但不改變 T20 的文章流程。
- T23：卡面圖像視覺規則（已完成）。不直接相關。
- **T28：卡片生活誌設計系統套用（2026-08-05 新增，草案待核准）**。「卡片生活誌」風格契約**已於 2026-08-05 由使用者完成並交付**（`docs/design-system/card-life-pop-style/`，v1 定稿），不再是規劃中的項目。T27 顯示元件須遵守該契約的色彩、框線、圓角與手機版規則，且契約已直接定下本模組的視覺規格與首頁版位（詳見待決問題 (e)）；本卡不自行重定義整站風格。分工：T28 負責版位與視覺預留，T27 負責背後的資料模型與後台管理。

## 已確認決策

- 首頁保留「本月情境選讀」模組；手機版同樣顯示，不因螢幕較小而移除。
- 內容不是固定「去旅行」，需要能隨月份或編輯規劃替換。
- 此模組應由後台或等效的可管理資料來源更新，不能要求每次更換內容都改程式碼並重新部署。
- 首頁其餘既有架構與資料流程不因本模組而移除。
- 本任務的正式視覺必須遵守「卡片生活誌」風格契約。**該契約已於 2026-08-05 交付並寫入專案文件**（`docs/design-system/card-life-pop-style/STYLE_CONTRACT.md`，v1），因此本條的原始前提（「契約尚未寫入正式專案文件前，不得把視覺示意圖當成程式實作規格」）已解除——契約本身即為可依循的正式規格。但仍須注意：契約明訂 **T27 未獲核准前只能做視覺預留**，不得硬編碼成正式資料功能、不得新增 schema 或後台 CRUD。

## 目標

讓管理者能建立、排程、替換或停用一筆首頁「本月情境選讀」內容，首頁只顯示目前生效且連結有效的內容；無生效內容時不留下空白區塊，既有首頁可正常運作。

## Scope（規劃內容；核准實作前不得執行）

若後續拍板通過，預期實作範圍包含：

- 新增獨立的首頁主題推薦資料模型（暫稱 `HomepageSpotlight`），不把首頁排程欄位硬塞進 `Article` 或 `SiteSetting`。
- 資料模型預期需能保存：小標、標題、摘要、按鈕文字、連結目標、是否啟用、開始／結束日期、排序或優先序，以及建立／更新時間。最終欄位、relation、index、default value 須經 schema 修改清單確認。
- 建立首頁讀取規則：只選取目前已啟用、在上架期間內、連結目標通過驗證的一筆內容；無符合資料時完整隱藏此模組。
- 建立後台建立、編輯、停用與預覽／檢查流程，讓管理者能更新每月主題而不必部署程式碼。
- 連結目標預期支援既有站內頁面，例如情境頁、攻略文章、優惠詳情或搜尋結果；具體欄位設計與可否支援外部網址仍待決。
- 在首頁主視覺與熱門情境之間加入模組，使用已確認的共用風格元件與手機版排版規則。
- 新增人工測試腳本，涵蓋建立、編輯、排程、生效、停用、無內容 fallback、行動版與連結導向。
- 依 schema 專門流程同步更新 `prisma/schema.prisma`、同版 schema 備份、schema 規格說明書、schema checklist 與必要 migration；每一項先列修改清單並取得確認。
- 完成後建立 T27 Summary，更新任務索引與 `CURRENT_STATE_目前專案狀態.md`。

## Non-scope

- 不進行整站「卡片生活誌」視覺重構；首頁與各詳情頁的共用設計系統屬相鄰但獨立的工作。
- 不修改既有 `Article` 的文章內容、情境標籤、分類、信用卡、優惠或 RewardTier 資料。
- 不新增個人化推薦、依使用者行為自動選題、A/B test、Email 推播或 CMS 多版內容工作流。
- 不建立新的公開 API、外部 CMS、第三方排程服務或 AI 自動產文流程。
- 不以 T27 名義重構全站導覽、麵包屑或銀行／卡片頁資訊架構；本卡只驗證選讀連結不會把使用者帶到缺乏可理解回路的頁面。
- 不處理 T22 排程資料更新、T24 申辦導引連結、T25 舊網址轉址、T26 GA 流量分析。
- 不由 AI 撰寫或發布真實的每月優惠內容；首筆實際內容需由使用者確認來源、文案與連結。
- 本草案不授權 schema、migration、資料庫、程式碼、環境變數、Git commit／push 或部署操作。

## 安全限制

- 本機 `.env` 的 `DATABASE_URL` 目前直接連到正式 Neon PostgreSQL。任何 Prisma migration、後台測試資料、seed 或資料寫入都可能影響正式站；未完成資料保護與回復方案前不得執行。
- schema 修改前必須依序讀取 `engineering-data-model-spec/schema修正原則.md`、目前 schema、最新版 schema 規格說明書與 schema checklist，列出完整修改清單並取得使用者確認。
- 第一次實作寫入前需取得 `.ai-worktree-lock.json`；若有其他 session 持有鎖或有重疊未提交變更，停止相關寫入。
- 後台權限沿用既有管理員登入邊界；不得新增公開寫入入口或繞過管理員驗證。
- 真實內容的連結目標須限制於已核准的站內路徑或經使用者確認的外部網址，避免形成任意導向或失效連結。

## 影響範圍

- 頁面與 route：首頁 `/`；既有後台新增或擴充首頁內容管理入口（具體 route 待決）。
- API：預期不建立公開 API；可能使用既有 Next.js server action／管理端 action，待實作設計確認。
- 資料模型與資料流：預期新增獨立首頁主題推薦 model；管理端儲存 → 生效條件篩選 → 首頁伺服端讀取 → 訪客導向既有目標頁。
- 共用元件：預期新增或擴充首頁編輯推薦元件；需引用已確認的風格 token／共用元件，不自行另起一套視覺規則。
- 文件與測試：schema 文件組、T27 人工測試腳本、T27 Summary、任務索引、CURRENT_STATE；自動驗證白名單需依當時政策確認。
- 外部服務：不涉及。

## 驗證方式與完成定義

本卡（規劃文件）的完成定義：使用者確認下列待決問題並明確核准 Scope 版本；此時才能產生 schema 修改清單與實作計畫。

實作階段的預期驗證方式（待 Scope 核准後再確認可執行指令與安全分類）：

- 自動驗證：`prisma validate`、`tsc --noEmit`、`next build`；僅在驗證政策分類有效、`.next` 與正式資料庫風險可控時執行。
- 資料層驗證：確認生效條件能正確選取一筆、排除未啟用／未到期／已過期資料，且無資料時首頁不顯示空區塊。
- 導覽回路驗收：每一筆已發布的選讀連結必須導向既有且可公開瀏覽的站內頁面；落地頁麵包屑只能呈現真實可抵達的資訊層級，不能出現沒有入口的假中間層。若落地內容涉及卡片、發卡銀行等關聯，頁面必須提供清楚且可點選的實際關聯入口。此項不要求 T27 重構全站導覽；若現有落地頁未符合規則，應先由共用導覽／資訊架構工作修正後，T27 才能通過該筆內容驗收。
- 人工驗收：管理者建立一筆草稿、設定排程、更新文字與站內連結、切換啟用狀態；桌機與手機首頁分別確認顯示、隱藏與導向正確。
- 部署驗證：實作完成且經核准部署後，於 Production 確認首頁只顯示預期內容，並由使用者登入後台驗收；本草案階段不適用。

## 資料保護與回復方式

- 本草案不讀寫資料庫、不建立 migration、不寫入真實首頁主題內容。
- 未來實作會新增可影響首頁顯示的資料，必須先決定正式 Neon PostgreSQL 的備份／回復方式，以及是否先建立獨立開發資料庫；在此風險未解決前，不得以正式站測試資料作為一般開發手段。
- migration 或資料填寫失敗時，回復方案、目標資料庫與責任人必須在 Scope 核准版本中明確記錄，不能事後猜測。
