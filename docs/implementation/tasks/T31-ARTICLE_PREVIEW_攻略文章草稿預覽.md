# T31 攻略文章草稿預覽

建立日期：2026-08-18（Asia/Taipei）
任務卡版本：v1（草案）
核准狀態：待核准
問題類型：功能需求（內容作業流程缺口）

> **狀態說明**：本任務卡只記錄規劃內容，**不構成任何實作授權**。使用者正式核准 Scope 之前，不得修改任何程式。

## 背景

2026-08-18 建立攻略文章上稿流程（`docs/sop/GUIDE_ARTICLE_PUBLISHING_攻略文章上稿流程.md`）時發現的缺口，
由使用者當場提問「草稿無法預覽該怎樣解決？」。

現況：

- `src/app/guides/[slug]/page.tsx:69` — `if (!article || !article.isPublished) notFound()`
- `src/app/guides/page.tsx:19` — 列表 `where: { isPublished: true }`

也就是**未發布的文章在前台完全不存在**。後台也只有純文字的 `<textarea>`，沒有任何渲染預覽。

### 為什麼這是真的問題

文章內文是 Markdown，實際呈現包含表格框線、清單、標題層級、FAQ 區塊、麵包屑與 JSON-LD。
**這些東西在 textarea 裡完全看不出來**，而目前唯一能看到成品的方法就是「先發布」。

先發布再修有三個實際代價：

1. 排版錯誤、錯字、死連結會**先被使用者與搜尋引擎看到**。
2. `toggleArticlePublish` 在**第一次發布時就寫死 `publishedAt`**（`src/lib/admin-actions.ts:572`），
   之後取消再重新發布也不會更新。所以「發布→發現有問題→取消→修好→再發布」會留下一個
   比實際上線日更早的發布日期。
3. 發布會觸發 `/sitemap.xml` 重新驗證，半成品可能被搜尋引擎抓走。

第 2 點特別容易被忽略：**它讓「先發布再修」不是無痕的**。

## 目標

讓作者在文章發布前，看到與正式頁面**完全相同**的呈現，且不對外公開。

## Scope（規劃內容；核准實作前不得執行）

### A. 抽出文章呈現元件

把 `guides/[slug]/page.tsx` 目前「取資料 + 渲染」混在一起的部分拆開，
渲染的部分抽成獨立元件（例如 `ArticleView`），讓正式頁與預覽頁共用**同一份**渲染程式。

這一步是關鍵：**若預覽用另一套渲染，預覽就失去意義**。

### B. 後台預覽路由

新增 `/admin/articles/[id]/preview`：

- 沿用既有後台登入保護（`getServerSession`），未登入直接擋掉。
- 不論 `isPublished` 為何都能看。
- 頁面上明確標示「這是預覽，尚未發布」，避免誤判已經上線。
- 後台文章列表與編輯頁加上「預覽」入口。

### C. 不進 sitemap、不被索引

預覽路由必須加 `robots: noindex`，且不得出現在 `sitemap.xml`。

### D. 文件

更新 `GUIDE_ARTICLE_PUBLISHING_攻略文章上稿流程.md`：把「草稿無法預覽」的限制改寫為預覽步驟，
並把「發布後立刻驗證」的多數項目前移到「發布前」。

## Non-scope

- 不做前台的 token 預覽連結（見待決問題 (a)）。
- 不做後台編輯器的即時 Markdown 預覽面板（見待決問題 (b)）。
- 不改 `Article` schema。
- 不改文章的發布邏輯或 `publishedAt` 行為（見待決問題 (c)）。
- 不處理優惠、卡片等其他內容型別的預覽。

## 已評估的替代方案

| 方案 | 優點 | 缺點 | 評估 |
|---|---|---|---|
| **(1) 後台預覽路由**（本卡 Scope B） | 是真實頁面；沿用既有登入，不新增攻擊面；實作單純 | 只有能登入後台的人看得到 | **建議採用** |
| (2) 前台 token 預覽連結 `?preview=xxx` | 可分享給沒有後台帳號的人審稿 | 需要 token 產生、失效與管理；token 外流等於文章外流 | 目前只有一位作者，複雜度不划算 |
| (3) 後台即時 Markdown 預覽面板 | 邊寫邊看，體驗最好 | **看不到最終頁面**（麵包屑、FAQ 區塊、頁面樣式、JSON-LD），解決不了根本問題 | 可作為 (1) 之後的加值 |
| (4) 維持現況，先發布再修 | 零成本 | 見「為什麼這是真的問題」三點代價 | 不建議 |

## 安全限制

- 預覽路由**必須**在登入保護之後，且必須 `noindex`。
- 不得因為預覽而放寬 `/guides/[slug]` 對未發布文章的擋掉邏輯——正式路由的行為維持不變。
- 不觸及資料庫寫入。

## 影響範圍

| 類型 | 檔案 |
|---|---|
| 新增 | `src/app/admin/articles/[id]/preview/page.tsx`、文章呈現元件 |
| 修改 | `src/app/guides/[slug]/page.tsx`（改用抽出的元件）、後台文章列表與編輯頁（加預覽入口） |
| 使用者可見 | 後台（新增預覽頁與入口）；**前台呈現不應有任何變化** |

## 驗證方式與完成定義

自動驗證：

1. `tsc --noEmit`、`next lint` 通過。
2. 未登入直接開預覽路由 → 被擋（不得回傳文章內容）。
3. 已發布文章的 `/guides/[slug]` 呈現與改動前**逐字相同**（抽元件不得改變輸出）。
4. `sitemap.xml` 不含任何 `/admin/**` 路徑。

人工驗收：

- 建立一篇草稿 → 從後台開預覽 → 確認表格、清單、標題、FAQ、連結都與發布後一致。
- 確認預覽頁有「尚未發布」標示。

## 風險與待決問題

| # | 問題 | 建議 |
|---|---|---|
| (a) | 要不要做「可分享的預覽連結」（不需後台帳號）？ | 建議先不做。目前只有一位作者，token 管理的複雜度與外流風險不划算 |
| (b) | 要不要一併做後台編輯器的即時 Markdown 預覽？ | 建議列為後續加值。它解決「邊寫邊看」，但解決不了「看到真實頁面」 |
| (c) | 要不要順便修正 `publishedAt` 在「取消發布再重新發布」時不更新的行為？ | 現行行為（保留第一次發布日）其實符合多數 CMS 慣例，但與「先發布再修」的實務衝突。**做完 T31 之後這個衝突就消失了**，建議不動 |
| (d) | 預覽頁要不要同時顯示 SEO 欄位與 JSON-LD 檢查結果？ | 對「AI 可引用性」這個產品目標有幫助，但會擴大 Scope，建議另議 |

風險：

- Scope A 動到已上線的 `/guides/[slug]`。抽元件必須是**純搬移**，不可順手改樣式或結構，
  否則會意外改動已上線頁面。驗證第 3 項就是為了擋這件事。
